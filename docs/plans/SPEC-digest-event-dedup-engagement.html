Spec — Morning Digest: Event Dedup + Engagement Signal

Step 4 / Step 6 selection fix · morning-digest cron · drafted 2026-06-10 · status: SPEC v3 — Pass-2 cleared (gate-driven placement pinned, multi-primary semantics stated); ready to build

The problem (observed, live)

Today's real run selected 5 near-identical "Anthropic ships Claude Fable 5" tweets as separate Top Stories — from tiny accounts with 0–1 likes:

1. @theshortcut  · 1 like  · A- (91)  "Anthropic releases Claude Fable 5, ... build playable video games"
3. @parody77647  · 0 likes · B+ (89)  "@sporadica Anthropic: Use our APIs ..."
4. @techsnif     · 0 likes · B+ (89)  "Anthropic releases two policy proposals ..."
5. @SOFXnetwork  · 0 likes · B+ (89)  "Anthropic on June 10 released Claude Fable 5 ..."
   (+ Also Noted: 2 MORE Fable-5 tweets)

One news event ate the entire digest, told 5–7 times by no-signal accounts. Two root causes:

  • No event-level dedup. Step 4 line 270 already says "cluster by underlying event/topic, keep the best source only" — the model ignores it. Prose instruction alone doesn't hold (same lesson as the echo bug & scoring inflation).
  • Engagement is computed but never used. likes/retweets are already on every X candidate (verified in _last_run_debug.json) — nothing in scoring or selection reads them, so a 0-like rewrite ties a 20k-like primary source.

Design principle

We've now proven the pattern three times on this cron (echo bug, format drift, score inflation): a prose instruction the model reliably ignores must become a deterministic guard. So the fix is split:

LayerWhatWhere
modelEmit an event_key per item + populate likes/retweets it already has. Soft guidance to prefer primary/high-signal sources.prompt.md Step 4/5
deterministicCollapse same-event_key items to one winner (engagement-weighted), enforce a per-event cap across the whole digest, apply an engagement tiebreak. Runs in the renderer's input path — model can't skip it.render_digest.py (pre-render pass) or a small select_digest.py

Rationale for putting the hard part in code: the model already had the clustering instruction and didn't follow it. Belt (prompt) + suspenders (code) — and the code is the load-bearing half.

Decisions needed from Ace

This is the judgment-heavy part. My recommended defaults are marked ◀ rec; tune any of them.

D1 — How aggressive is event dedup?

Option A
1 item per event, hard. Same event → only the single best item survives, everywhere (Top + Also Noted). ◀ rec
Option B
1 in Top Stories, but allow 1 more of the same event in Also Noted if it adds a genuinely different angle.
Option C
Max 2 per event in Top Stories (looser).

Rec A: today proved that "the same news 5 ways" is pure noise. If an event truly deserves two slots, it's rare; start strict, loosen if you miss coverage.

D2 — How is the "event" identified?

Mechanism
Model emits a short normalized event_key per candidate (e.g. "claude-fable-5-launch", "gemma-4-release"). Deterministic pass groups by exact event_key.
Fallback
If event_key missing, derive a key from a normalized title/tweet-text shingle (lowercased, stopword-stripped, first ~6 significant tokens) so dedup still fires when the model forgets. ◀ rec include fallback

Model-supplied key is more accurate; the shingle fallback guarantees the guard never silently no-ops. Both, with key winning.

D3 — Engagement: signal weight & how it's used

As tiebreak only
Engagement only breaks ties when picking the winner within an event cluster and ordering equal-score items. Does NOT change base score. ◀ rec
As a scoring input
Fold a log10(likes+retweets) bump into the score (e.g. +0 to +6). More impactful, but risks re-introducing inflation and biasing toward virality over substance.

Rec tiebreak-only: Ace explicitly values substance over virality (a 0-like Karpathy gem should still win). Engagement is a quality prior for picking among near-duplicates, not a popularity contest. Within an event cluster, prefer: primary/official source > higher engagement > more informative text.

D4 — Low-engagement floor for X?

Soft
No floor; engagement only matters relatively (tiebreak). A 0-like primary-source launch tweet can still be Top if nothing better covers it. ◀ rec
Hard
X items under N (e.g. 25) likes get a score cap (e.g. max 82) unless from a thought-leader/tracked handle. Risks suppressing early-but-important posts.

Rec soft: a hard floor would have killed the legitimately-useful Karpathy-style low-engagement post. The real problem today was duplication, not low engagement per se — D1+D3 already fix it.

Proposed implementation

1 · Prompt changes (prompt.md, config-class — backed up, diff-shown)

  • Step 4: require an event_key on every surviving candidate; restate (briefly) that the deterministic pass will collapse duplicates so the model should still try to pick the best source.
  • Step 5/7 schema: add event_key, ensure likes/retweets are carried into _render_input.json (already in pipeline; just thread them through — they're already in the tweet shape).
  • Step 6: note that final event-dedup + engagement tiebreak is enforced downstream, not by hand.

2 · Deterministic selection pass (code, the load-bearing half)

A pure function run over selected + also before render (added to render_digest.py, fully unit-tested like the rest):

def dedup_and_rank(items, per_event_cap=1):
    # 1. assign event key: item.event_key or shingle_fallback(text)
    # 2. group by event key
    # 3. within each group pick winner:
    #      is_primary > final_score > engagement > text-len > tweet_id  (RC2 total order)
    # 4. keep top `per_event_cap` per event, drop the rest (log dropped_reason="event_dup", lost_to_url)
    # 5. placement is GATE-DRIVEN by each winner's final_score: >=83 -> Top, 77-82 -> Also.
    #    NOT rank-bucketing — a 78 winner never gets promoted into Top just because Top is underfilled.
    # returns (kept_top, kept_also, dropped[])  — dropped surfaced in debug dump
  • Applies across Top + Also Noted as one pool (so the same event can't appear once in each), then re-splits gate-driven — each surviving winner is placed by its own final_score against the fixed 83/77 gates (≥83→Top, 77–82→Also), never by rank-bucketing into a fixed top-5.
  • Everything dropped is logged to _last_run_debug.json with dropped_reason="event_dup" + the winner it lost to — so "why did my tweet get cut?" is always answerable from disk (consistent with existing observability).
  • Idempotent + order-stable; no network, no model call.

RC1 — is_primary defined deterministically (fixes Blocker 1)

Belt + suspenders, mirroring D2: is_primary = (item.get("is_primary") is True) or (authorHandle.lower() in PRIMARY_HANDLES).

  • PRIMARY_HANDLES = a small, version-controlled, reviewable allowlist file (config/primary-handles.txt in the repo, one handle per line, comment-able) — NOT an inline literal in render_digest.py (Config-Drift lens). Seeds: the AI-lab/official accounts (anthropicai, openai, googledeepmind, googleai, meta, mistralai, xai, huggingface, …) plus Ace's existing thought-leaders.txt handles (loaded + unioned at runtime so the list doesn't rot in two places).
  • The model MAY also set is_primary: true in the Step-5 schema when it knows a post is the official/origin source; the allowlist is the backstop when it doesn't.
  • If neither fires, is_primary=False and the item competes on score→engagement→text — a 0-like genuine launch from an allowlisted handle still wins its cluster, satisfying D4 no-floor.

RC2 — winner-selection and placement use the SAME score-aware comparator (fixes Blocker 2)

The Pass-1 catch: choosing a cluster winner by source>engagement>text could discard the 83+ Top-tier version and bury the event in Also Noted. Fix — one total order, score outranks engagement:

winner / sort key (descending):
  1. is_primary            (True > False)
  2. final_score           (the 83/77 gate field — so the Top-worthy version wins its cluster)
  3. engagement = likes+retweets
  4. text length (more informative)
  5. tweet_id / url ascending   # RC4 total-order tiebreak → fully deterministic/idempotent

Placement is then derived from the surviving winner's own final_score against the existing 83 (Top) / 77 (Also) gates — never re-derived, never demoted by the dedup step. An event with a Top-worthy member keeps a Top slot.

Multi-primary clusters: when ≥2 items in a cluster are is_primary (common now that thought-leaders.txt is unioned in — a tracked builder's take + the official post), key-1 ties and final_score (key 2) decides. This is intended: the higher-scored primary wins, whether that's the official launch or a high-signal thought-leader field report. We do NOT force the official-origin post to always beat a better-scored primary take.

RC3 — shingle fallback gets an explicit similarity threshold + conservative-merge rule (fixes Blocker 3)

The real trap is in today's pool: "Anthropic releases two policy proposals" (#4) is a DIFFERENT event from "Anthropic ships Fable 5" but shares {anthropic, release, …}. Fix:

  • Group by exact event_key when present. Only when an item lacks event_key, fall back to a token-set Jaccard over significant tokens (lowercased, stopword-stripped, handles/URLs removed) with an explicit threshold ≥ 0.6.
  • Conservative bias (HARD RULE): when in doubt, DO NOT merge. A missed duplicate is cosmetic; a false merge silently deletes real news. Below-threshold = distinct events.
  • Unit test from today's real pool: Fable-5 items (#1,#3,#5) MUST group; policy-proposals (#4) MUST stay separate.

RC4 — total-order tiebreak (fixes idempotency gap)

Today three items tied at score 89 with 0 likes — score+engagement alone is not a total order. The final tweet_id/url ascending key (key 5 above) makes output fully deterministic and stable across reruns.

RC5 — reuse existing observability, name the new field (fixes enum drift)

  • The existing dropped_reason enum already has topic_dup. The event-dedup drop reuses a clear value: event_dup is ADDED to the enum (and the debug-dump consumer + self-test fixtures updated) — topic_dup is left for the model's own topic-diversity drops so the two mechanisms stay distinguishable in the debug dump.
  • Each dropped duplicate records a new lost_to_url key naming the winner it lost to, so "why was my item cut?" is answerable from _last_run_debug.json (consistent with the 7-day-pruned debug contract).

QA additions (Pass-1 QA lens)

  • Same-org-different-event: #4 policy-proposals must NOT merge into Fable-5.
  • Event spanning Top+Also where the Also-tier member has higher engagement → primary/score still wins, event keeps its Top slot.
  • All-items-tie (score+engagement) → deterministic order by tweet_id.
  • Empty/degenerate pool → dedup_and_rank([]) == ([],[]), no crash.
  • Ordering: dedup_and_rank runs BEFORE the "NO HOLLOW DIGESTS" empty-result check, so if dedup collapses everything below 77 the honest-line husk still triggers.
