## Required Changes

1. **The `os.path.realpath` identity key is not stable across the fleet's actual topology — D-2 will mis-dedup or fail-to-dedup the same doc (D-2, INV-4).** The key is `sha1(os.path.realpath(src))[:12]`. Two concrete failure modes the closeout ("share the same file twice → identical slug") won't catch because it tests one host, one path: (a) The **same logical doc lives at different absolute paths** — an Obsidian note reached via the vault mount on the Studio vs a git-mirror checkout path on another Mac realpaths differently → two cards for one doc, the exact dup INV-4 claims to prevent. (b) `realpath` **resolves symlinks**, so a doc shared through a symlinked convenience path vs its canonical path dedups correctly — but a doc whose canonical location itself moves under a stable symlink changes key and orphans. State explicitly that D-2 dedup is **per-host, per-absolute-path** and does not span the vault's multiple mount points, OR key on a normalized logical identity (vault-relative / repo-relative when detectable, realpath only as the fallback). As written, INV-4's "same on-disk source file → same slug" is only true within a single host's single path to that file.

2. **The `/tmp` → fresh-slug rule silently defeats dedup for the most common ad-hoc path, and the classifier is unspecified (D-2, INV-4).** "Generated / transient input (`/tmp/*`, temp render, stdin, `--fresh`)" gets a fresh timestamp slug. But *how does the backend decide a path is transient?* A prefix match on `/tmp`, `/var/folders` (macOS's real temp dir — `/tmp` is a symlink to `/private/tmp`, and `mktemp` on macOS returns `/var/folders/...`), `$TMPDIR`? If the classifier only checks literal `/tmp/`, macOS-native temp renders fall through to the **real-source** branch and get a realpath-dedup key on an ephemeral path that won't exist next run → an accreting pile of orphan cards. Specify the transient-detection predicate explicitly (enumerate the temp roots incl. `$TMPDIR`/`/var/folders`, or make transient the *default* and real-source the opt-in via an explicit flag/detected-existing-tracked-file). This is the seam most likely to produce the dup-card outcome the whole D-2 rule exists to prevent.

3. **INV-3's "delivered, not just emitted" #alerts proof needs a concrete capture mechanism in the AC, not just the word "received" (INV-3, §10 AC-3).** The intent is right (delivery-path integrity, matching the fleet's alert-delivery-path-integrity discipline), but "a **received** #alerts message" as an acceptance line has no stated capture method — a closeout can trivially satisfy it by asserting notify.py exited 0, which is exactly the emitted-not-delivered trap. Require the AC to name the check: read back the message from the #alerts channel by ID (or the notify skill's delivery-confirm receipt), and assert on the round-tripped content. Otherwise INV-3's headline guarantee is self-certified.

4. **Rename-orphan cleanup is emitted as a "note," never actioned — INV-6 idempotency and the clean-index goal quietly rot (D-2, INV-6).** D-2 says a rename/move "changes the key → orphans the old card (importer/CLI emits a `renamed_from→to` note so the stale card can be deleted)." Emitting a note is not cleanup; nothing deletes the orphan. Over months of re-shares this reintroduces exactly the dup-card clutter R3/R4 aim to prevent, just via renames instead of collisions. Either (a) have the importer auto-soft-delete the orphaned slug when it detects a `renamed_from` with a resolvable old key, or (b) explicitly accept orphan accretion as a known cost and say who reconciles it and how often. Don't leave it as an un-actioned log line dressed as a mitigation.

## Lens Notes (one line each)
- **Architecture:** Scope-collapse (remove sensitivity tower once exposure accepted) is the correct simplification; the identity-key layer is now the only non-trivial seam and it's under-specified for the fleet's multi-mount reality.
- **Security/identity-isolation:** Flip is a genuine tightening (public→LAN); INV-2 secret-scan-on-every-path correctly retained as defense-in-depth, not load-bearing — sound.
- **DevOps/SRE:** `.bak` rollback + canary "fallback-fired" signal are good; the alert-delivery AC must name its capture method or it's self-certified (RC-3).
- **Implementation/maintainability:** Committing `backfill.py` to `deploy/docs-ace/` closes the runtime-`var/` drift vector; the transient-vs-real classifier (RC-2) is the maintainability landmine.
- **QA:** Backfill E2E (rich doc, idempotency, delete) are real gates; the D-2 dedup AC tests only the single-host happy path and won't catch the multi-mount/temp-root failures (RC-1/RC-2).
- **Config-drift:** Salt pinned to the existing D-11 location + scripts committed — drift vectors closed; INV-5 grep-proof that briefs bypass doc-share is the right structural guarantee.

## Residual Risks / Open Questions
- OQ4=(A) accept-LAN-readable is load-bearing for the entire simplification: if Ace ever reverses it, the sensitivity tower has to come back — worth a one-line note that the removal is *conditional on accept*, so a future reversal knows what it's re-adding.
- D-2's realpath key across the Obsidian-Sync topology (vault present on multiple Macs via different mounts) — does a doc shared from the Studio vs the MacBook dedup, or two-card? (RC-1.) The backfill runs on one host so it's latent until an ad-hoc live re-share from a second host.
- No cap/quota on backfill manifest size beyond "curated" — if the approved manifest is large, is there a rate/credit consideration on `ace_publisher.py`, or is it purely local render (no external cost)? Confirm the backfill has no per-item external spend so R4's "flood" is only an index-hygiene concern, not a cost one.
- Does `privacy-scan.sh`'s existing pattern set actually flag a bare 1Password UUID / internal hostname in a `report`-type doc, or only literal secrets? Not load-bearing now (exposure accepted), but it's the one thing standing between a LAN reader and an accidentally-pasted token — worth confirming its pattern coverage before the flip, since it's now the *only* content gate.
