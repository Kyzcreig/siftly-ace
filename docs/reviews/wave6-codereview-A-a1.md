## Findings (severity-ordered)

### HIGH-1 — Shadow leaks the embed number into the brief via `affinity_source="embed"` (scripts/pf-score.py, `apply_shadow_affinity` + `score_candidates`)
AC1 says: under `shadow` the returned delta must be byte-identical to pre-Wave6 keyword, embed written ONLY to the audit artifact. The delta is preserved correctly — `apply_shadow_affinity` starts from `out = dict(item)` (keyword item) and only adds `shadow_*` keys, so `personal_fit_delta/raw/affinity` stay keyword. Good.

But `score_candidates` returns `"embed"` as the top-level `affinity_source` for shadow, AND `apply_shadow_affinity` overwrites the per-item `affinity_source` to `"embed"`. The brief consumer reads `affinity_source` to decide provenance/labeling. In shadow the *number* it serves is keyword, but it is now **labeled `embed`**. That is a leak of embed state into the returned (brief-facing) payload — the brief will report it ran on embeddings when it did not. The missed branch: every test asserts `shadow.affinity_source === 'embed'` — i.e. the test *enshrines the bug* rather than catching it. Pre-Wave6 byte-identity of the *returned object* is broken: a new top-level key `affinity_source:"embed"`, plus `shadow_*`, `embedding_affinity`, `keyword_secondary_affinity`, `vec_metric`, and mutated `signals` are all injected into the returned items, not just the audit. AC1's "byte-identical to pre-Wave6 + embed only to audit" is violated on the returned payload.

Correct shadow contract: returned `affinity_source` must be `"keyword"`/`"keyword_fallback"` (whatever pre-Wave6 emitted), shadow fields must be stripped from the brief-returned items and injected by `pf-audit.py` only. As written, the brief and audit consume the *same* item dicts.

### HIGH-2 — Shadow is NOT fail-safe: an embed failure flips the served label and is not recorded as `keyword_fallback` correctly vs. the success path (scripts/pf-score.py, `score_candidates`)
On embed failure the except returns `(items, "keyword_fallback", str(e), None)` — good, that branch is correct and `affinity_source="keyword_fallback"`. BUT on embed *success* in shadow it returns `"embed"`. So the served label depends on whether the embed helper succeeded — meaning shadow's brief-facing output is non-deterministic w.r.t. embed health, which is exactly what AC1 forbids (shadow must be invariant to embed). The fail-safe AC3 is only half-met: it records `keyword_fallback` on failure (correct) but corrupts the label on success. No test exercises the shadow+embed-failure branch (only `PF_EMBED_AFFINITY_FORCE_FAILURE` is defined but never invoked in the provided test). Missed branch.

### HIGH-3 — L2→similarity monotonicity / normalization is asserted nowhere; unnormalized vectors silently produce garbage (src/lib/vec-metric.ts + the TS helper)
`vec-metric.ts` only exports the string literal `'l2norm'`. The conversion from L2 distance to a `score` lives in `vec.ts`'s store (not shown), and the helper consumes `neighbor.score` blindly. L2 distance is monotonic-with-cosine **only for L2-normalized vectors** (‖a−b‖² = 2−2cos θ iff ‖a‖=‖b‖=1). The `KeywordEmbeddingProvider` returns raw 0/1 term-presence vectors — magnitude varies with how many terms match (e.g. `[1,1,1,0]` has ‖·‖=√3, `[1,0,0,0]` has ‖·‖=1). These are **not** normalized, so for the keyword test provider the L2→similarity mapping is *not* monotonic-with-cosine. The test "passes" only because the toy vectors happen to rank the way the assertion wants — it does not assert the metric is correct, only that delta>0. No test asserts: (a) vectors are normalized before insert/query, (b) score is monotonic-decreasing in L2 distance, (c) the real `createEmbeddingProviderFromEnv` output is normalized. The AC4 requirement "is the chosen metric asserted in a test?" is met only at the trivial string level (`expect(SIFTLY_VEC_METRIC).toBe('l2norm')`) — the *semantics* are unasserted. This is the classic silent-garbage branch.

### MED-4 — Default-shadow on malformed config is correct, but env precedence has a footgun (scripts/pf-score.py, `load_affinity_mode` / `normalize_affinity_mode`)
`normalize_affinity_mode` correctly falls back to `"shadow"` for absent/garbage values (empty string, unknown mode, None). Default-when-absent: ✓. BUT: `env = os.environ.get("PF_AFFINITY_MODE") or os.environ.get("SIFTLY_PF_AFFINITY_MODE")` — an **empty-string** `PF_AFFINITY_MODE=""` is falsy, so it silently falls through to the secondary env var, then to config, then to default. A deliberately-set empty primary var being overridden by a stale secondary var is surprising. More importantly `if env is not None:` never fires for `PF_AFFINITY_MODE=""` because the `or` already collapsed it to the second var / None. Minor, but it means you cannot force "use config" by blanking the primary env. Low blast radius (still lands on shadow), hence MED not HIGH. No test covers empty-string or malformed env/config.

### MED-5 — `embed` mode combines embed + 0.2·keyword, so "embed" is never pure embed; shadow's audit delta therefore isn't a clean embed signal (scripts/pf-score.py, `apply_embed_affinity`)
`combined_affinity = clamp(embed_affinity + 0.2 * keyword_affinity)`. The audited shadow delta is this blend, not the embed-only number. If the audit's purpose (AC1) is to compare pure-embed vs keyword before promotion, blending 0.2·keyword in pollutes the comparison — you can't attribute a shadow win to embeddings. Also the `+` (not weighted average) can push affinity past the keyword baseline purely from the keyword term, and the clamp masks it. Document/justify the 0.2 blend or record `embedding_affinity` (raw) as the comparison field — which it does store, so at least the raw embed number survives to audit. Downgraded to MED because the raw is preserved.

### MED-6 — HKV weighting applied as confidence weight: correct, but TOP_K truncation happens AFTER weight filtering and can starve the aggregate (TS helper, `main`)
`sourceWeight` (bookmark 1.0 / like 0.3 / else 0) is used as a weight in `sum(score*weight)/sum(weight)` — ✓ it's a confidence weight, not a label, AC5 met. BUT the loop does `if (weight<=0) continue; ...; if (weighted.length>=TOP_K) break` over `neighbors` ordered by KNN distance. If the nearest 5 neighbors are all non-bookmark/like (weight 0), they're skipped and TOP_K is filled from farther neighbors — fine. But if fewer than TOP_K positive neighbors exist among all 50, `weightSum>0` still holds on ≥1 and it proceeds; if ZERO positive neighbors it `throw`s → whole candidate fails → entire helper exits non-zero → Python falls back to keyword for ALL candidates (AC3 fallback fires, recorded). Acceptable fail-safe, but one bad candidate nukes embed for the whole batch. No per-candidate isolation. Missed branch: a batch with one zero-positive-neighbor candidate.

### LOW-7 — `affinity_source="sentinel"` for `PF_WEIGHT=0` is a new field in the kill-switch path (scripts/pf-score.py, `score_candidate`)
AC2: `PF_WEIGHT=0` must be byte-identical. `delta = raw*0 = 0` ✓, `personal_fit_delta=0.0` ✓. But the returned item now carries a brand-new `affinity_source:"sentinel"` key (and top-level `affinity_mode`, `affinity_source`) absent pre-Wave6. If "byte-identical output" means the JSON the brief consumes, it is NOT byte-identical — new keys added. If it means only the numeric delta, ✓. The PRD says "byte-identical output" — confirm scope. The provided tests assert delta equality, never key-set equality. Missed branch.

### LOW-8 — `vec.ts` re-export is harmless but unguarded for search-path byte-identity (src/lib/vec.ts)
The only change is `export { SIFTLY_VEC_METRIC } from './vec-metric'` — a pure additive re-export, no runtime/search-path change. AC6 satisfied in the diff shown. Caveat: the L2→score conversion that actually matters for X byte-identity lives in the un-shown body of `vec.ts`; the diff doesn't prove the existing search path is untouched, only that this one line is additive. Cannot fully clear AC6 from the diff alone.

## Required Changes
1. **(HIGH-1/HIGH-2)** Shadow must return the keyword `affinity_source` (`"keyword"`/`"keyword_fallback"`), never `"embed"`, at both top-level and per-item. Strip ALL embed/shadow fields (`shadow_*`, `embedding_affinity`, `keyword_secondary_affinity`, `vec_metric`) from the brief-returned items; inject them into the audit artifact inside `pf-audit.py` from a separate channel, not by sharing the same item dicts. Fix the tests to assert shadow `affinity_source !== 'embed'` and brief byte-identity of the returned item key-set vs pre-Wave6.
2. **(HIGH-3)** Add a test asserting: (a) embedding vectors are L2-normalized before upsert/query, (b) `score` is strictly monotonic-decreasing in L2 distance, (c) the real env provider output is normalized. Assert the metric *semantics*, not just the string. If `vec.ts` does not normalize, normalize at insert+query or BLOCK promotion of embed/shadow.
3. **(HIGH-2/AC3)** Add explicit tests for the embed-failure branch in BOTH `embed` and `shadow` modes (use `PF_EMBED_AFFINITY_FORCE_FAILURE=1`): assert exit 0, `affinity_source="keyword_fallback"`, `embed_error` populated, and brief delta byte-identical to keyword. Confirm the helper ALWAYS exits 0 — note `main.catch` sets `process.exitCode=1` (non-zero), which is the *helper* process; Python catches it and falls back, so the *brief* survives — verify this chain in a test.
4. **(MED-4)** Add env/config tests: absent, empty-string, malformed JSON, unknown mode → all must land on `shadow`. Decide empty-primary-env precedence intentionally.
5. **(MED-5)** Document/justify the `embed + 0.2*keyword` blend, or expose pure-embed delta in the audit so promotion decisions use a clean signal.
6. **(LOW-7)** Confirm "byte-identical" scope for `PF_WEIGHT=0` and shadow; if key-set matters, gate the new keys behind audit-only emission.

## Lens Notes
- **Security:** stdin JSON is `JSON.parse`'d unbounded and SQL uses parameterized `placeholders()` (good, no injection). `--eval` of a large embedded TS string is awkward but not user-controlled. No new exfil surface.
- **Correctness:** the central defect is provenance/label leakage in shadow (HIGH-1/2) and unasserted metric semantics (HIGH-3). The numeric delta path is actually correct; the *labels and contract* are not.
- **Maintainability:** brief and audit sharing the same mutated item dicts is the root cause — separate them. The 800-char embedded TS-in-Python heredoc is a maintenance hazard; extract to a real `.ts` file run via tsx.
- **Test-coverage:** tests exercise only the happy embed+shadow+keyword path with toy normalized-enough vectors; they MISS embed-failure fallback, malformed config/env, key-set byte-identity, metric normalization/monotonicity, zero-positive-neighbor candidates, and `PF_WEIGHT=0` shadow interaction. The shadow test actively *asserts the buggy `affinity_source="embed"`*, so green here is a false negative.

Note on grounding: I'm reviewing the diff as provided; the L2→score conversion body of `vec.ts` and `createEmbeddingProviderFromEnv` are referenced but not shown, so HIGH-3 and LOW-8 are flagged as unproven-from-diff rather than confirmed-broken — that uncertainty is itself a BLOCK reason (a load-bearing scorer's metric correctness must be provable from the changeset + its tests, and here it is not).
