## Required Changes

**1. The OFF_TOPIC_REPO_MARKER substring match will false-floor genuine on-topic repos — `meshery` and the embedded-substring problem (B.2a).**
B.2a says markers "match as case-insensitive **substrings** of the description." Substring matching against a hand-picked consumer-domain set is fragile in the exact direction that fails *closed on a good item*:
- `"tool"` is named in B.2a's prose list? No — but `"server"` adjacency: `music-assistant/server` is floored via `"media library"`, fine. The real hazard is short markers as substrings: `"tv"` (from "tv channel") is a substring of countless on-topic words; `"iptv"` is safe but if the set is "data-driven and easily extended," the next maintainer adds `"tv"` or `"ai"`-adjacent generic and silently floors AI repos. **Pin the matching to word-boundary or whole-phrase markers, not raw `in` substring**, and add a selftest asserting `meshery`/`SkillSpector`/`chatwoot`-vs-`chat` do not collide. (`chatwoot` is listed as OFF via `"live-chat"`/`"omni-channel"` — good — but `"live-chat"` as a bare substring vs a legit "chat agent" AI repo is exactly the collision to pin.) This is fail-toward-**exclusion**, so it's safe-direction, but it can suppress genuine recoveries the spec claims (`meshery` ON), making §3's "genuine on-topic recover" assertion false on extension.

**2. B.2a marker check ordering vs the OFF_TOPIC_MARKER (insult) path is specified only for github, leaving a gap if a github description carries an insult marker (B.2a, A.2).**
B.2a places `OFF_TOPIC_REPO_MARKERS` "BEFORE the generic-token check." But the spec does not state its order relative to the *existing* `OFF_TOPIC_MARKERS` (politics/insult) check, nor relative to the `has_on_topic_token` short-circuit. Walk the evidence-pack `python_on_topic` for a github item: `has_on_topic_token` is computed first and returns `(None,None)` on ANY on-topic token — so a github repo whose description is `"open-source tool to own the libs, AI-powered"` short-circuits to model-label BEFORE either marker check fires. The spec must state explicitly where the github repo-marker force-off sits in the existing flow (the evidence pack shows the current flow has NO github-specific branch yet), and confirm the politics/insult `OFF_TOPIC_MARKERS` force-off still applies to github descriptions. Right now Part B's marker logic is described in prose but not located in the actual control flow shown in the evidence pack — an implementer could place it after the token short-circuit and silently let a generic-token-bearing off-topic repo through.

**3. The thin-pool probe asserts a gate-clearance invariant but does not pin the scores it depends on (§4 thin-pool probe, B.2a).**
The degraded-pool probe is the right fix for the Pass-1 fake-green. But "assert NO github off-topic repo clears ALSO_GATE at either regime (45/50)" re-introduces a pool-conditional assertion unless the probe **fixes the pool composition** it tests against. B.2a's own evidence says the generic-token repos score 59–60 — *above* both gates — and are only saved by markers. So the probe's pass depends entirely on `OFF_TOPIC_REPO_MARKERS` catching every such repo. Required: the probe must (a) run with markers ON, (b) assert each *known* generic-token repo (freeCodeCamp, optimizerDuck, music-assistant, chatwoot) is floored by a marker (not by ranking), and (c) include at least one synthetic off-topic repo whose description has NO marker and a generic token, proving the *residual* leak is bounded — or acknowledging it as accepted residual. Without (c), the probe proves the markers you wrote catch the repos you knew about — a tautology, not an invariant.

**4. Empty-summary fail-safe is correct but the structural-fragment path for github is under-specified (B.4, A.3).**
B.4 says empty github summary → `_topic_text` = slug → floored. But `is_structural_fragment` for a github item is governed by `is_topic_curated_source`, which is **False for github** (Part A, B.5). So github goes through `is_bare_fragment(text)` — and the spec must state which text: `_item_text` (slug only) or `_topic_text` (title+summary)? B.2 says `_topic_text` is used by `is_structural_fragment`. So a github repo with a *rich* description is NOT a fragment (good), but an empty-summary github repo with a non-empty slug → `_topic_text`=slug → `is_bare_fragment("trycua/cua")`: does a slug count as a bare fragment? The evidence-pack `is_structural_fragment` returns `is_bare_fragment(text)` for non-curated sources, and the X-tuned `is_bare_fragment` is what floored the slugs in the first place (§1: 24 fragment-floored). So **empty-summary github correctly floors via fragment** — but a *populated*-summary github now passes `title+summary` to `is_bare_fragment`, which may now read as non-fragment for repos that were previously fragment-floored. That's the intended recovery, but the spec never states that `is_structural_fragment` for github reads `_topic_text` (the only thing making `SkillSpector` non-fragment). Make B.2/A.3 explicit: **github fragment verdict reads `_topic_text`; that is the mechanism of fragment recovery, not just the off-topic recovery.**
