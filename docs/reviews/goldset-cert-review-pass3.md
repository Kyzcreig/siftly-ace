## Critical Blockers

1. **Bar 3's synthetic-neutral mutation tests the harness's OWN injected fixture, not the engine's neutral-handling — D-4 bar-strength note / D-12 / Phase 2.** v3's fix for Bar 3 untestability is to mutate a *synthetic injected neutral* into TOP for the `--mutate bar3` case "only (not in the certified set)." This proves the bar3 *assertion logic* fires when something it's watching crosses TOP_GATE — but it does **not** prove the bar is load-bearing over the *certified fixture*, because (per D-12's own admission) every production neutral is floor-pinned. So the honest state is: **Bar 3 is structurally-satisfied on the certified set (like Bar 1), and its mutation exercises injected scaffolding, not the real pool.** That's defensible — but D-4 still lists Bar 3 alongside the load-bearing bars without the same blunt "nearly true by construction" verdict Bar 1 gets. A reader of D-4 comes away believing Bar 3 is a live net over the fixture. Required: state plainly in D-4 that Bar 3 is structurally-satisfied on the certified set (mutation is on scaffolding) — give it Bar 1's honesty, don't let the synthetic-mutation dress it as load-bearing.

2. **The no-leak assertion as specified cannot actually catch in-process constant leak — Phase 2 / Phase 3.** v3 makes each mutation a separate `subprocess.run([... "--mutate", bar])` AND asserts "the clean ratified-set run passes identically whether or not the mutation cases ran first." But if every mutation already runs in its own subprocess (the B3 fix), the parent pytest process *never* mutates a constant, so the clean run is **trivially** identical regardless of order — the no-leak assertion is vacuously true and proves nothing. The assertion only has teeth against the failure mode it names (module-constant bleed) if the mutations could run in-process. As written, two correct-but-redundant guards are presented as one guard validating the other. Required: either (a) drop the no-leak *assertion* as redundant once subprocess-isolation is mandated (subprocess isolation IS the guarantee — say so), or (b) if the no-leak assertion is meant to defend a future refactor that drops subprocesses, run *one* mutation deliberately in-process and assert the clean run still passes — otherwise the assertion is theater.

Drop the "identical whether or not the matrix ran first" claim as vacuous under subprocess isolation, OR convert it into a real test by running exactly one mutation in-process with explicit save/restore and asserting the restore worked. Don't present a vacuous assertion as a leak guard. (Closes Blocker 2.)

3. **Pin the gate read to `select_shadow`'s resolved value, name the symbol (D-10).** D-10 says "define once, feed both." Tighten: name *where* the single value lives — the harness captures the literals it passes as `top_gate`/`also_gate` into `select_shadow`, reads the engine's resolved module gates (FACT 5: tiebreak 49/45 at L70-75) via the engine's own accessor (not a re-typed `49`/`45`), and asserts equality. The expected `49/45` literal must appear in exactly one place; the pin compares engine-resolved to that one literal. As written D-10 still permits two typed literals (the one fed in, the one asserted) drifting.

4. **Disambiguate Bar 1's placement framing under MAX_TOP (D-4.1 / D-11).** D-11 fixes Bar 2 (score) cleanly, but Bar 1 ("zero known_bad in TOP within MAX_TOP slots") evaluates on *placement* — and on a 15-item pool, forced-distribution could fill MAX_TOP with known_goods and *evict* a known_bad that scored above TOP_GATE down into ALSO/neither. That known_bad cleared TOP_GATE *by score* but isn't *placed* in TOP, so placement-framed Bar 1 reads green while the real regression (a known_bad scoring TOP-worthy) is live. Specify: Bar 1 should assert **no known_bad clears TOP_GATE by score** (the regression that matters), not merely "no known_bad lands in a TOP slot." Otherwise slot-cap eviction masks the exact inversion the gate exists to catch.

5. **Confirm the harness runs after the JS selftests in the `&&` chain (D-5/DevOps).** D-5 mandates an explicit `&&` chain so a non-zero harness exit fails `npm run verify`. Add the ordering constraint: the Python gold gate runs *after* `tsc`/lint/vitest so a cheap fast-fail short-circuits before the heavier gold scoring — and confirm the gold harness's own Python deps are import-only (no network) so it can't hang CI.
