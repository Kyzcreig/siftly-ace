# Independent Senior Review

## Verdict
BLOCK

## Critical Blockers

1. **A1 can silently change what posts before promotion — the shadow gate is contradicted by the swarm scope itself (§3.1 + §4 + §6 P0 vs §1.2 / evidence pf-score.py:24).** The shadow-mode story claims A1 "scores in parallel, changes nothing" until promoted. But P0 rewrites the affinity body of `pf-score.py` *in place* — the same file the LIVE crons invoke via pf-audit.py with the default `PF_WEIGHT=30`. There is no shadow harness specced that runs the NEW code path while the live brief keeps calling the OLD one. Once the swarm merges the new affinity into pf-score.py, the very next live cron run uses it at full weight — unless `PF_WEIGHT=0` is set in `brief-config.json` for the duration. The PRD never says the kill-switch is engaged during shadow. "Run A1 in shadow against `_last_run_debug.json`" describes an analysis artifact, not an isolation boundary. **Premise verified:** evidence shows pf-score.py is the live-invoked file and `PF_WEIGHT=0 → byte-identical`; the PRD relies on a knob it never instructs anyone to set. This is the data-path-into-production blocker.

2. **§5 AC#1's "hard-fail if it silently falls back" is in direct tension with §3.1's keyword fallback — the safety net defeats its own proof.** Evidence (vec.ts:105) confirms the store *silently demotes to bruteforce on any failure*, and the e2e gate hard-fails only if `SIFTLY_SQLITE_VEC_EXTENSION_PATH` is set AND it demotes. But §3.1's fail-safe says embedding/vec failure → "fall back to the existing keyword affinity." So in production (where that env var is typically unset), a vec store demotion or KNN error makes pf silently revert to keyword affinity at full PF_WEIGHT=30 — i.e., A1 is "live" but invisibly serving the OLD signal, and no alert fires. AC#1 proves the embedding path *in the test rig*; it proves nothing about the live cron. There is no production telemetry requirement that the embedding path was actually taken. **This is a wrong-product-in-prod risk masked as a passing gate.**

3. **§3.4 cross-brief dedup is shared mutable state with an unspecified concurrency/canonicalization model — clobber + stale-read race.** Two independent crons (morning-digest, x-feed-brief) both "consult+update" `cross-brief-seen.json`. The PRD names no locking, no atomic read-modify-write, no per-PT-day key scoping, and no eviction. A JSON file read-modify-written by two processes = last-writer-wins clobber if they ever overlap; even serial, there is no specified TTL so the store grows unbounded and a stale entry from a prior day suppresses a legitimately re-surfacing story. "(or sqlite table)" is left as an unresolved either/or in a load-bearing shared-state design. **Data-correctness blocker; must be specced as atomic + day-scoped + bounded before build.**

4. **§3.5 eval is partially circular and cannot cleanly separate A1 from baseline before promotion.** The AUC is specced as "pf-score separating held-out positives from random feed items." A1's affinity *is* mean-cosine-to-positives; "random feed items" as the negative class makes A1 look strong almost by construction (random items are far from the positive cloud in the same embedding space A1 optimizes). The keyword baseline is scored on the *same* positives/negatives. This measures "does embedding-distance separate saved-from-random" (trivially yes) — not "does A1 rank Ace's real brief better than keyword." The honest discriminator is the held-out **organic saves vs. hard negatives Ace saw-and-didn't-save**, which §3.7 explicitly defers to P2. So at P0 there is no non-circular negative set. **The eval that gates promotion can pass vacuously in A1's favor.**

5. **Write-scope collision: A1 (pf-score.py) and the eval/A-B harness both depend on the affinity function, and the gold-set adversarial case (AC#3) cannot be authored until A1 exists — these are not disjoint, they are serially dependent.** §6 P0 lists A1, eval harness, and the AC#3 "bad-item-near-positive" gold case as one parallel wave. But AC#3's adversarial item must be selected *against A1's embedding space* (an item that embeds near a positive), which doesn't exist until A1 is written. And the A/B harness imports the same affinity code A1 is mutating. Two swarm tasks editing/depending on the same `pf-score.py` contract in parallel = merge race or a vacuous test written against the old keyword path. **Must be serialized: A1 → then eval/gold-case against A1.**

6. **AC#2 ("PF_WEIGHT=0 byte-identical") is a vacuous gate as the *only* regression proof.** It is true by construction per the evidence (delta 0 → identical) and proves nothing about A1's actual output. The only criterion that proves A1 is *safe at weight* is the ≥3-run shadow output-text diff in AC#8 — but that's gated to P1 and is observe-only with no numeric tolerance (how much drift is acceptable? which items flipping above/below the 49/45 / 58/50 gates counts as a regression?). **A pass/fail gate watched only for PASS, with no defined fail condition, is not a gate.**

## Required Changes

1. **Make shadow isolation a code boundary, not a config hope.** Either (a) the swarm writes the new affinity behind an explicit `PF_AFFINITY_MODE={keyword|embed|shadow}` flag where `shadow` computes BOTH and writes the embed result only to the audit artifact while returning the keyword delta to the brief; OR (b) P0 is required to set `PF_WEIGHT=0` in `brief-config.json` as its first action and AC#8 must prove the live config has PF_WEIGHT=0 for the shadow window. State explicitly which. The merge of new code must not change live output by default.

2. **Add a production telemetry assertion to AC#1:** pf-score.py must emit `affinity_source: "embed"|"keyword_fallback"|"sentinel"` into the pf-audit proof artifact every run, and a cheap check (cron-observability or a gold-run assertion) must alert if live runs show `keyword_fallback` after promotion. Without this, blocker #2 stands — the fallback is invisible.

3. **Spec the dedup store concretely:** sqlite table (not JSON), key = `(pt_day, url_canon_hash)`, atomic upsert under a transaction, explicit TTL/eviction (drop rows older than N PT-days), and define read-then-write ordering so the second brief of the day reads the first's writes. Drop the "(or JSON)" fork. Define canonicalization precisely (which params strip, host-case, fragment) and unit-test the UTM + reworded-title cases (already in AC#5 — keep) plus a same-day-both-briefs concurrency test.

4. **Replace the circular AUC negative class.** At P0, the only honest negatives available are items Ace *saw and did not save* (organic skips), not random feed items. If those aren't labeled yet, then the A/B promotion decision cannot be made at P0 — say so, and make labeling the saw-didn't-save set a P0 deliverable (it's the same labeling effort §3.5 already calls for to reach 150–300 items). Until then, A1 stays shadow-only and promotion is explicitly deferred.

5. **Serialize the P0 wave:** (i) A1 affinity rewrite → (ii) eval harness + AC#3 adversarial gold case authored against A1's space → (iii) A/B. Mark these dependent, not parallel. The independent-and-parallel tasks are: gatherers (reddit/github-trending/X-search), engagement-normalize lib, dedup lib, diversity lib — those touch disjoint new files and can run concurrently.

6. **Give AC#8 a numeric fail condition:** define shadow regression as "no item crosses its TOP/ALSO gate (49/45 digest, 58/50 x-feed) in a direction it wouldn't have under keyword-pf in >X% of items across 3 runs," and name X. An observe-only diff is not acceptance.

7. **Confirm gatherer write-scope disjointness in the PRD:** state that `gather/reddit.*`, `gather/github-trending.*`, `lib/engagement-normalize.*`, `lib/cross-brief-dedup.*`, `lib/diversity-rerank.*`, `eval/rank_metrics.py` are all NEW files, and that `pf-score.py` is the ONLY shared mutable surface (touched solely by A1). Explicitly assert no task regenerates score_digest.py or the vec schema.

## Lens Notes
- **Product:** Right problem (keyword→embedding pf is the real gap), but "ship A1 only if it wins nDCG/AUC" rests on an eval that can't yet make that call honestly — promotion criteria is softer than it reads.
- **Architecture:** Additive-term discipline preserved; the architectural sin is putting shadow-mode in config-space instead of code-space, so "shadow" isn't structurally guaranteed.
- **Security:** Low surface; GitHub Trending HTML scrape and Reddit free tier are unauthenticated reads — pin a parser-failure-degrades path (AC#4 covers crash; add malformed-HTML).
- **Infra:** Shared JSON state across two crons with no locking is the classic two-writer file-corruption setup; sqlite + transaction removes it.
- **DevOps:** No launchd/cron mutation by swarm — good; but `npm run verify` (AC#8) bundling e2e that hard-fails on vec-demote will be flaky in CI unless the extension path is guaranteed provisioned in the runner — pin it.
- **Implementation:** HKV weighting is specced in the right place (weights in the cosine aggregation, label stays binary) — statistically sound. mean-top-k (k=5 of k≈50 KNN) is reasonable; confirm cosine, not L2 distance, since vec.ts KNN returns `knn.distance`.
- **QA:** Three of eight ACs (1 partial, 2, 8) can pass without proving A1 is correct-and-safe in production; the gold adversarial case is the only one with real teeth and it's blocked on A1 existing first.

## Open Questions
1. During the shadow window, is `PF_WEIGHT=0` set live, or does shadow run as a separate code path? (Determines whether blocker #1 is real or already mitigated.)
2. Does `vec.ts` KNN return cosine distance or L2? A1's `cosine` aggregation assumes cosine; if the store is L2/`vec_distance_L2`, the weighted-mean and the 0.92–0.95 cluster thresholds (§3.4 Stage 3) are wrong.
3. Are the "saw-and-didn't-save" organic skips labelable at P0, or is the only available negative set "random feed"? (Determines whether promotion can happen at all in this wave.)
4. What is the acceptable shadow-drift tolerance (items flipping gates) before A1 is allowed to promote — and who signs off on the 3-run diff?
5. Is `SIFTLY_SQLITE_VEC_EXTENSION_PATH` set in the live cron environment? If not, the AC#1 hard-fail gate never arms in production, and blocker #2's silent-fallback is the default behavior.
