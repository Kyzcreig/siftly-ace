## New Defects (introduced by v2 fixes)

**1. AC#9's 10% tolerance has no defined denominator or per-brief split — the numeric gate is numerically ambiguous.** "No more than X% of items cross their gate" — X% **of what?** Of all scored candidates that run? Of items near the gate? Per-brief or pooled across digest + x-feed? The two briefs have different gates (49/45 vs 58/50) and very different candidate volumes (x-feed pulls a 24h firehose; digest a curated discovery set), so a pooled 10% is dominated by the larger pool and can mask a total flip on the smaller brief. The fix that closed Blocker #6 introduced a gate that can pass or fail depending on an unstated denominator. **Required:** define the denominator explicitly (recommend: per-brief, `crossings / items_scored_that_run`, max over the ≥3 runs, not averaged) so the gate is computable and not gameable by pooling.

**2. The `shadow` default creates a test-gap / dead-code risk for the `embed` path that no swarm test exercises end-to-end on the live cron.** AC#1 proves the embed path "when provisioned" via a real-vec e2e in CI; AC#2 proves `shadow` returns the keyword delta. But nothing in P0 ever runs the **embed branch through the actual pf-audit artifact path with real candidates** — `embed` only executes in shadow as a write-to-artifact side path, and promotion to `embed`-as-return is deferred to P1/gated. So the branch that will eventually drive live output is exercised only by a unit e2e, never by a shadow run producing comparable numbers, until the gated promote. That's acceptable IF the shadow runs actually compute and persist the embed delta for the AC#9 diff — but AC#9's comparison ("direction they wouldn't have under keyword-pf") **requires the embed number to be computed every shadow run**, which AC#2 only guarantees the keyword number is *returned*. **Required:** state explicitly that under `shadow` the embed delta is computed AND persisted to the audit artifact every run (not lazily/optionally), because AC#9's diff is otherwise un-sourced. (§3.1 says "write the embed result ONLY to the pf-audit artifact" — good — but AC#2/AC#9 don't bind that the embed value feeding the AC#9 diff is the same persisted artifact value. Tie them.)

**3. The cosine-vs-L2 requirement is stated as testable but the §3.4 Stage-3 dedup threshold can still silently inherit the wrong space.** §3.1 correctly requires the build pick one metric and "assert it in a test" (AC#1: "a unit test asserts the chosen metric"). That part is genuinely testable. **But** §3.4 Stage 3 says the headline-cluster cosine threshold "assumes a COSINE space; if the vec store is L2 … normalize first or convert." Stage 3 is marked "(optional, later)," so no AC covers it — yet it reads the SAME vec store A1 configures. If A1 lands on **L2-normalized vectors** (the cheaper of the two options §3.1 offers) rather than a `distance_metric=cosine` migration, then a later Stage-3 implementer applying a raw 0.92–0.95 cosine threshold against an L2-distance KNN is the exact bug §3.1 warns about, re-introduced one section later with no test. **Required:** make the chosen-metric decision a single recorded fact (e.g. a constant/migration both §3.1 and §3.4 read) so Stage 3 cannot pick a different assumption. Low severity (Stage 3 is deferred) but it's a latent contradiction the v2 dedup section introduced.

**4. The sqlite dedup migration vs the existing vec migration — collision is *claimed* avoided but not *proven* in the text.** §6 asserts *"the dedup migration is its OWN new table, not the bookmark vec table."* Evidence confirms the vec store uses `bookmark_vec_idmap` (renamed off vec0's shadow table) — so `cross_brief_seen` is a distinct name, good. **But** the PRD never states **which sqlite database file** the dedup table lives in. If `cross_brief_seen` is created in the **same DB file** as the sqlite-vec store, its migration runs in a DB that loads the vec0 extension, and a migration-runner that doesn't load the extension (or loads it in a different order) can fail to open the DB at all (vec0 virtual tables require the extension present to even read the schema). If it's a **separate DB file**, no issue. The fix that closed Blocker #3 (sqlite table + its own migration) didn't specify the DB-file boundary. **Required:** state that `cross_brief_seen` lives in its own dedicated sqlite file (or a non-vec DB), NOT the sqlite-vec store DB, so the new migration never has to open a vec0-extension-dependent schema.

**5. Chicken-and-egg between "saw-didn't-save" labeling and the 14-day grace — flagged but the timeline math isn't closed.** §3.5 sources organic-skip negatives from *"items that appeared in past briefs / timeline pulls and were never bookmarked/liked after the 14-day grace."* §3.7 repeats the 14-day grace for the passive loop. The honest deferral language ("if unlabelable at P0, promotion deferred") covers the *decision*, but there's a quieter trap: the negative set requires items that are **both** (a) ≥14 days past their surfacing AND (b) have surfacing provenance recorded. If `origin: brief-surfaced` tagging only started recently (§3.7 says it builds on an "EXISTING" tag — good, but no date), the eligible pool at P0 may be near-zero even though the mechanism "exists." This isn't a contradiction, but the v2 fix leans the whole promotion decision on a labeled set whose **availability is asserted, not sized.** **Required (or Open Question):** state the count of currently-eligible saw-didn't-save items (past briefs ≥14d old with provenance) so "label ≥150" is known-feasible, not hoped — otherwise promotion is structurally deferred and the PRD should say so up front rather than discovering it at P0.

## Required Changes
1. **AC#9:** define the 10% denominator explicitly — per-brief (not pooled), `gate-crossings / items_scored_that_run`, evaluated as the max over the ≥3 runs. (New Defect #1)
2. **AC#2 + AC#9:** bind that under `shadow` the embed delta is *computed and persisted to the pf-audit artifact every run*, and that AC#9's diff reads that persisted value — so the promotion gate has a defined data source. (New Defect #2)
3. **§3.1 + §3.4:** record the cosine-vs-L2 choice as a single shared fact (constant or migration both sections read); forbid Stage-3 dedup from assuming a different space than A1 chose. (New Defect #3)
4. **§3.4 / §6:** state that `cross_brief_seen` lives in its own sqlite DB file, not the sqlite-vec store DB, so its migration never opens a vec0-extension-dependent schema. (New Defect #4)
5. **§3.5:** state the current count of eligible saw-didn't-save items (≥14d-old surfaced items with provenance); if it can't reach ~150, say promotion is deferred by construction in this wave. (New Defect #5)

## Open Questions
1. Does `cross_brief_seen` share the sqlite-vec store's DB file or get its own? (Determines whether RC#4 is a real migration hazard or already safe.)
2. When did `origin: brief-surfaced` provenance tagging actually begin, and how many surfaced-and-unsaved items are ≥14 days old today? (Determines whether the P0 eval can decide promotion at all, vs. structural deferral.)
3. Did A1 choose `distance_metric=cosine` on the vec table or L2-normalized vectors? The choice is left open in §3.1 and silently load-bears on §3.4 Stage 3.
4. Is the AC#9 10% tolerance evaluated per-brief or pooled? (RC#1 — the gate is not computable until this is fixed.)
5. Does the shadow run persist the *embed* delta (not just the keyword delta it returns) to the audit artifact on every run, so the AC#9 diff has a source? (RC#2.)
