# Event-Dedup Spec — Senior Review (Pass 1)

## Verdict
BLOCK / APPROVE WITH CHANGES — **APPROVE WITH CHANGES**. The design knobs are right; the *deterministic pass as written* has three correctness holes that will ship a wrong digest if built verbatim. None require redesign — they require pinning down underspecified comparators and one merge-order bug. Fix the Required Changes and it's a green build.

## Critical Blockers

1. **"primary/official source" is the FIRST tiebreak key but is never defined — and that's the one thing D3/D4 say MUST be load-bearing.** (Spec §"Proposed implementation 2", winner rule `primary/official source > higher engagement > more informative text`; D3 rec "primary/official source > higher engagement"; D4 rec "a 0-like primary-source launch tweet can still be Top"). The whole no-floor safety argument rests on the primary-source post beating the 0-like dupes. But the candidate fields in the EVIDENCE PACK (`title,url,source,authorHandle,...`) contain **no `is_primary` / `is_official` boolean**. `source` is just `'X'` for every tweet — it does not distinguish @AnthropicAI from @parody77647. So as written, the very first comparator in the winner rule is unresolvable, and the function silently falls through to "higher engagement" — which on a day where the real primary post has 0–1 likes (exactly today's case) means a no-signal rewrite with more likes can win, or worse, the 20k-like field report beats the official launch. **This is the exact failure D3/D4 promise to prevent, reintroduced through an undefined comparator.**

2. **Cross-pool merge "re-splits by score" can demote the surviving primary item OUT of Top Stories — silently violating the 83 gate semantics.** (Spec §"Proposed implementation 2": "Applies across Top + Also Noted as one pool, then re-splits"). The pass collapses an event spanning Top+Also into one winner — correct. But the winner is chosen by `source > engagement > text`, **not by score**. So you can pick a winner whose `final_score` is the Also-Noted-tier item (77–82) and discard the 83+ Top item from the same event. After "re-split by score desc," that survivor lands in Also Noted, and the event vanishes from Top Stories entirely — even though a Top-worthy version existed. The winner-selection comparator and the placement comparator disagree, and the spec never reconciles them. Result: an event that *should* headline gets buried, or the digest under-fills Top. **This is a lossy-digest bug.**

3. **Shingle fallback over-groups distinct same-org events on a heavy-news day.** (Spec §D2 fallback: "first ~6 significant tokens" shingle). Today's real pool already contains the trap: item #4 is "Anthropic releases two **policy proposals**" — a genuinely different event from "Anthropic releases Claude Fable 5." After lowercase + stopword strip + first-6-tokens, both shingle to roughly `{anthropic, release, claude, ...}` / `{anthropic, release, policy, proposal}` — high token overlap, same org, same day. A first-6-token shingle with no similarity *threshold* (the spec says "derive a key," implying exact-match grouping on the shingle string, but never states the match rule) will either collapse policy-proposals INTO the Fable-5 cluster (false merge → real news lost) or not group the 0-like Fable dupes that paraphrase heavily (false split → today's bug survives). **The fallback as specified has no tunable similarity boundary, so it cannot be correct for both cases simultaneously.**

## Required Changes

1. **Define `is_primary` deterministically and make it the comparator, not the word "official."** Two concrete options, pick one in the spec before build: (a) a tracked-handle allowlist (the "thought-leader/tracked handle" set D4 already references — @AnthropicAI, @OpenAI, @GoogleDeepMind, the lab/builder accounts) → `is_primary = authorHandle in PRIMARY_HANDLES`; or (b) a `is_primary` boolean the model emits in Step 5 schema alongside `event_key`. Recommend **both** (model hint + allowlist backstop), mirroring the D2 belt+suspenders pattern. Without this, Blocker 1 ships.

2. **Make winner-selection and placement use the SAME score-aware comparator.** Within an event cluster, pick the winner by: `is_primary desc → final_score desc → engagement desc → text length desc`. Score must outrank engagement so the 83+ version of an event wins its own cluster and stays in Top. State explicitly: the surviving winner's *placement* (Top vs Also) is determined by **that winner's `final_score`** against the 83/77 gates — not re-derived. This closes Blocker 2.

3. **Specify the shingle MATCH rule and a guard against same-org false-merge.** Don't key on first-6-tokens equality. Use Jaccard/token-set similarity over the significant-token set with an explicit threshold (e.g. group if Jaccard ≥ 0.6), AND require shingle-fallback grouping to be **conservative** (when in doubt, DON'T merge — a missed dup is a cosmetic flaw; a false merge silently deletes real news). Add a unit test from today's pool asserting Fable-5 (#1,#3,#5) groups together while policy-proposals (#4) stays separate. This closes Blocker 3.

4. **Tiebreak determinism for true ties.** D-spec and §2 step 5 say "engagement desc as tiebreak" but two items can tie on score AND engagement (today: three items at 89, likes∈{0}). Append a final stable key — `tweet_id`/`url` ascending — so output is fully deterministic and idempotent across runs. (Stated as a goal — "Idempotent + order-stable" — but unreachable without a total order.)

5. **Reuse the existing `dropped_reason` enum, don't add a parallel value.** §2 says log `dropped_reason="event_dup"`, but the EVIDENCE PACK shows the existing enum is `selected_top|also_noted|below_83|below_77|topic_dup|seen_dedupe`. There is already a `topic_dup`. Decide: extend the enum with `event_dup` (and update the debug-dump consumer + the 37 self-tests' fixtures) OR reuse `topic_dup`. Don't ship a value the debug tooling doesn't know. Also confirm the "+ the winner it lost to" field is a NEW key — name it (`lost_to_url`) so it's queryable.

## Lens Notes
- **Product:** Correct call to fix duplication not low-engagement (D4 soft) — but the digest's job is "best version of each event"; Blocker 2 risks the *best* version losing to a lesser same-event item, which is the product regression in disguise.
- **Architecture:** Sound — pure function in the renderer input path, no network/model, single dedup pool then split. The one-pool-then-resplit is the right shape; just make the split score-driven (RC2).
- **Implementation/Maintainability:** `dedup_and_rank` is clean and unit-testable, but its winner comparator hides three undefined predicates (`primary`, shingle-match, total-order). Underspecified comparators are the classic source of "works in test, wrong in prod."
- **QA:** Test list is good but missing the adversarial cases that matter: same-org-different-event (#4 vs Fable), event spanning Top+Also where the Also item has higher engagement, all-items-tie, and empty pool → must return `([],[])` not crash.
- **Config-Drift:** prompt.md is config-class (backup + diff-show ✓). The real drift risk is the **PRIMARY_HANDLES allowlist** — that's a new list that will rot. Put it where it's reviewable and version it; don't bury it inline in render_digest.py as a literal.
