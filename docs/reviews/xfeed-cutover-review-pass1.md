## Critical Blockers

1. **#1 soft-fail design is non-functional as specified — the shown stage loop has no try/catch, so a `profile` throw still aborts the whole run (PRD §1.3.1 vs evidence "stage loop aborts on throw").** The evidence shows the loop as `for (const stage of stages) { … const stageResult = await runStage(stage, …); mergeSourceRows(…); stagesRun.push(…) }` with **zero** error handling inside the loop body. A throw from `runStage` propagates straight out of `runDailyIngest`. The PRD says "the loop catches throws from soft stages, records them in the result, and continues" — but that catch **does not exist yet** and the PRD lists it as a one-line aside ("Implementation: a per-stage `soft?` flag … the loop catches throws"). This is the load-bearing change, not a detail. Worse: `export` runs *before* `profile`, so on the happy path this is fine — but the PRD's claim "the run still returns `ok:true` with `export` already complete" is only true *if* the new try/catch is actually wired AND placed so it doesn't also swallow the `abortController` timeout throw (`if (abortController.signal.aborted) throw timeoutFailure(...)` is inside the same loop). A naive `try { … } catch` around the loop body would catch the timeout-abort throw on the `profile` iteration too and mislabel a wall-budget timeout as a soft profile-stage failure. **Spec the exact loop edit, including how it distinguishes a soft-stage failure from an abort-signal timeout.**

2. **Parameterizing `MAX_TOP/MAX_ALSO/TOP_GATE/ALSO_GATE` risks silently regressing the LIVE morning-digest because these are module-level constants read at import time, and derived constants (`LOW_REACH_SCORE_CAP = ALSO_GATE - 5`) and the self-test invariants depend on them (PRD §2.2.4 / §2.5-P2.1 vs evidence lines 71–76, 134, 304, 566–567, 584).** `select_shadow` (line 485) reads `MAX_TOP/MAX_ALSO/TOP_GATE/ALSO_GATE` as **free module globals** (lines 523–525, 534–536), and `select_digest.build_render_input` calls `_sd.select_shadow(pool, …)` with **no gate/cap arguments** (evidence: `selected, also, discarded, _meta = _sd.select_shadow(pool, tl_handles, tl_aliases, tracked, now=now)`). If parameterization is done by mutating module globals (the obvious quick path), x-feed and morning-digest run in the **same Python process only if they don't** — but if any shared harness imports both, or x-feed sets globals that persist, morning-digest's gates corrupt. If done by adding params with defaults, you must thread them through `select_shadow` **and** recompute `LOW_REACH_SCORE_CAP` (line 134, currently `ALSO_GATE - 5` at module scope — it will NOT pick up an overridden `also_gate` unless explicitly recomputed inside the function). The self-test at lines 566–567/584 asserts `LOW_REACH_SCORE_CAP < ALSO_GATE` and `ALSO_GATE <= TOP_GATE` against the **module constants**, not the params — so it does not actually test the parameterized path. **This is the single highest regression risk to a live brief and the PRD treats it as "safe, no behavior change" (§2.5-P2.1) without proving global-vs-param isolation.**

3. **Shadow-first rollout does NOT contain the prompt label-emission change — the prompt edit ships to the LIVE x-feed cron the moment it's saved, before any gate/engine flip (PRD §2.2.1 + §2.2.6 vs §2.5 phasing).** §2.5-P2.2 says "x-feed label-emission prompt change behind a shadow path (compute, don't post)" — but a cron *prompt.md* is read by the live cron run; there is no "shadow prompt" unless you fork the prompt file or branch on a flag *inside* the prompt. §2.2.1 says keep `base_score` "as an advisory/audit field only" while the **legacy selector still posts off `base_score`**. If the model is told to stop producing reliable per-metric ratings and start emitting enum labels, the legacy prose path's `base_score` quality may degrade (the model now optimizes for labels) **while it is still the thing being posted**. The PRD never specifies whether shadow runs a *separate* prompt or the same prompt that the live post also consumes. **As written, P2.2 leaks the scoring-instruction change into the live post before P2.4's gate.**

4. **Gate re-derivation acceptance ("cardinality parity") can certify a wrong-but-same-volume selection as correct (PRD §2.2.3 + §2.5-P2.3 + Open Q2).** "Re-derive so the deterministic engine selects ~the same VOLUME" only constrains count, not membership. The whole point of the cutover is to *change which tweets win* (kill engagement-gamed/recency-inflated picks). Tuning gates until cardinality matches will, by construction, push gates to admit the same number — potentially re-admitting exactly the gamed tweets the engine was supposed to drop. The acceptance target contradicts the stated goal (§2.1: "can still be gamed by purchased engagement"). **Parity is a sanity floor, not an acceptance criterion.**

5. **Provenance assertion (#1) reads the file the stage just wrote, but there's no spec for *when*/*how* it reads it relative to the atomic rename — and a soft-failed assertion that "alerts but returns ok:true" can report a healthy run while the on-disk profile is stale/contaminated (PRD §1.3.2 + §1.3.3).** If the atomic write fails (rename throws) the prior profile survives (good), but the provenance assert then reads the *old* file — which may itself be `whole-corpus`/contaminated from a prior manual run — and either (a) passes against stale-but-correct data, masking that today's rebuild produced nothing, or (b) fails and soft-alerts while the pipeline reports `ok:true`. Either way "ok:true + #alerts fired" is the success-while-doing-nothing pattern the focus list calls out. **The assert must distinguish "today's rebuild wrote a valid brief-relevant-only profile" from "an old valid profile happens to be on disk."**

## Required Changes

1. **Show the exact stage-loop diff.** Add `soft?: boolean` to `DailyIngestStageCommand`, and rewrite the loop body to: check `abortController.signal.aborted` → `throw timeoutFailure` (unchanged, BEFORE the try); then `try { stageResult = await runStage(...) } catch (err) { if (stage.soft) { record soft failure on result; alert; continue } else { throw } }`. Explicitly place the abort-signal check **outside** the try so a timeout is never reclassified as a soft failure. Add an assertion test that a timeout during the `profile` stage still surfaces as a `timeout`/`pipeline` failure, not a swallowed soft failure.

2. **Parameterize via explicit function arguments, never global mutation, and recompute derived values inside the function.** Change `select_shadow(pool, …, *, max_top=MAX_TOP, max_also=MAX_ALSO, top_gate=None, also_gate=None)` where `top_gate/also_gate` default to the mode-aware module constants when `None`, and compute `low_reach_cap = also_gate - 5` **locally**. Thread the same overrides through `build_render_input(..., max_top=None, max_also=None, top_gate=None, also_gate=None)` and pass them into the `_sd.select_shadow(...)` call. Add an explicit regression test: call `build_render_input(engine="deterministic")` with **no** overrides and assert byte-identical selection to the pre-change morning-digest selftest on a frozen fixture. Forbid any code path that assigns to the module globals.

3. **Make the shadow path use a separate prompt artifact, not the live one.** Either fork `prompt.md` → `prompt.shadow.md` for the shadow window (live cron keeps the unchanged prose prompt), or have the cron emit **both** the legacy ratings AND the new enum labels in one run (additive prompt change that does not remove the per-metric ratings), so the live `base_score` selector is provably unchanged during shadow. Only at P2.4 do you remove the legacy ratings. Specify which.

4. **Replace "cardinality parity" with a membership + quality acceptance.** Acceptance = on N recent snapshots, the deterministic selection (a) drops every tweet the legacy path admitted that fails a known guard (engagement-gamed, off-topic/political, fragment), and (b) is within ±1 volume. Report the membership diff (added/removed with reasons), not just counts. If the goal is "tighten," state the target volume explicitly (Open Q2) before deriving gates — don't back into it.

5. **Provenance assert must verify *freshness* + *mode* of the just-written file.** After the atomic rename, re-read the final path and assert BOTH `signal_basis.mode === 'brief-relevant-only'` AND `updated_at` ≈ this run's wall clock (e.g. within the run window). A stale-but-valid profile must soft-fail loudly, not pass. The soft-failure result must carry a distinguishable reason (`profile-stale` vs `profile-contaminated` vs `profile-write-failed`) so the #alerts message is actionable.

6. **State the morning-digest vs x-feed process isolation explicitly.** Confirm the two briefs never share a Python process/import graph at runtime (separate cron invocations). If they can co-run or share a harness, the param-only design is mandatory and global mutation must be statically prohibited (add a test that imports both and asserts gate constants are untouched after an x-feed call).

## Lens Notes
- **Product:** Cardinality-parity acceptance (§2.2.3) actively undermines the product goal of de-gaming x-feed; parity should be a floor, membership-quality the target (Open Q2 must be answered before P2.3).
- **Architecture:** `LOW_REACH_SCORE_CAP = ALSO_GATE - 5` at module scope (evidence line 134) means gate overrides won't propagate to the cap unless recomputed in-function — a latent correctness bug in the parameterization plan.
- **Security:** Untrusted tweet text drives enum-label emission; ensure the deterministic Python override (off-topic/fragment/political → forced drop) runs *after* the model labels and cannot be talked out of a drop by adversarial tweet content — same threat model morning-digest's §395 hardening addresses.
- **Infra:** New `profile` stage runs inside the 20-min wall budget after `export`; verify the abort-signal check still fires on the `profile` iteration so a hung profile rebuild can't blow the budget silently.
- **DevOps:** P2.2 "compute, don't post" is not achievable with a single live `prompt.md`; needs a forked/flagged prompt or it's a live change mislabeled as shadow.
- **Implementation:** The soft-fail try/catch, the param threading through `select_shadow`→`build_render_input`, and the in-function `low_reach_cap` recompute are the three edits that must be shown as diffs, not described.
- **QA:** Existing self-tests (evidence 566–567/584) assert against module constants, so they will pass green while the *parameterized* path is untested — add fixture-based tests that exercise the override path AND a no-override byte-identical regression for morning-digest.
