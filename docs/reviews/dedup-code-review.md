# Dedup Code Review

## Verdict
**APPROVE WITH CHANGES** — no shipping blocker, but two correctness bugs (one tiebreak-inversion, one ASCII-only id assumption) and a real ALSO-leak gap that the 52/52 self-test doesn't cover.

## Findings

**1. [HIGH] `_neg_stable` tiebreak is INVERTED → violates the stated spec.** `dedup_and_rank.__doc__` and your test "all-tie deterministic by tweet_id" promise the *lower* id wins. The chain: outer sort is `reverse=True`; the key is `(_winner_sort_key, _neg_stable)`; `_neg_stable("a")=(-97,)`, `_neg_stable("b")=(-98,)`. Under `reverse=True`, the *larger* tuple sorts first, and `(-97,) > (-98,)`, so id `"a"` (smaller) wins. **That's correct — for equal-length ids.** But unequal-length ids break it: `_neg_stable("ab")=(-97,-98)` vs `_neg_stable("a")=(-97,)`. Python compares `(-97,-98)` vs `(-97,)` → the shorter tuple is the prefix, so `(-97,) < (-97,-98)`, meaning under reverse `"ab"` sorts before `"a"`. So id `"a"` loses to `"ab"`. Lexicographic "smaller id first" says `"a" < "ab"` → `"a"` should win. **Inverted for the prefix case.** Tweet ids are equal-width snowflakes today, so the test passes by accident; the moment a `url` fallback id (variable length) is the `_stable_key`, the tiebreak silently flips. *Fix:* drop the hand-rolled `_neg_stable` entirely and do a two-pass stable sort — sort ascending by `_stable_key` first, then sort by `_winner_sort_key` with `reverse=True` (Python's sort is stable, so equal-key items retain the id-ascending order). Concretely:
```python
ordered = sorted(items, key=_stable_key)
ordered.sort(key=lambda it: _winner_sort_key(it, primary_handles), reverse=True)
```
This is provably "lower id first among equals" for any string length and removes the per-char tuple entirely.

**2. [MED] `_neg_stable` is ASCII/BMP-fragile.** `tuple(-ord(c) for c in ...)` on an emoji/astral id or a URL with percent-encoded unicode produces large negative codepoints — still total-orders, but combined with Finding 1 the ordering is non-obvious and untested. The two-pass fix above eliminates this too (plain string comparison is well-defined).

**3. [MED] ALSO-leak: gate placement uses winner's score, but the WINNER may not be the highest-scoring item in the group.** `_winner_sort_key` ranks `is_primary` *above* `final_score`. So a 0-score primary can beat a 79-score non-primary dup (your "0-like primary beats viral dup" test — intended). But then placement is `_score_val(winner) >= TOP_GATE`: the surviving winner carries the *primary's* low score, so a genuine 79→Also event whose primary author scored 60 lands in Also at score 60 — fine. The real leak is the inverse: **a group whose best-by-gate item (score 84, Top-worthy) is NOT primary gets collapsed to a primary winner scoring 70 → the 84-worthy event is now represented in Also, and the 84 item is in `dropped`.** A Top story silently demotes to Also (Blocker-2 says winner chosen by priority, placed by own score — this is *spec-conformant by the letter*, but it's the buried-Top-item failure mode your hunt #3 asked for, and it's untested). Decide explicitly: if the event is Top-worthy by *any* member, the survivor should be placed in Top (place by `max(_score_val(m) for m in group)`), or document that primary-author preference can demote an event's tier. Right now it's an undocumented demote.

**4. [MED] OVER-group risk: `_shared_distinctive` only requires ONE shared distinctive bigram, and the bigram can be (distinctive, generic).** `_distinctive_bigrams` keeps `("fable", "released")` (non-generic + generic, `len("fable")>=3`). Two *different* Fable-product tweets — say "Fable released" and "Fable retired" — share no bigram, fine. But "Claude Opus released" and "Claude Haiku released" both yield `("claude","opus")`/`("claude","haiku")` — distinct, won't merge, good. The adversarial merge is a *shared distinctive-but-common entity bigram*: "Claude Code ships X" and "Claude Code ships Y" both contain `("claude","code")` → merged as same event even when X and Y are unrelated Claude-Code stories. `("claude","code")` is exactly the kind of product phrase that recurs across distinct same-product events. One shared product bigram is a weak same-event signal. *Mitigation:* require either (a) ≥2 shared distinctive bigrams, or (b) a shared bigram where *both* tokens are non-generic AND the union isn't a known recurring product name. At minimum, log merges so OVER-grouping (real-news deletion — the worse failure) is auditable. Severity MED not HIGH because PER_EVENT_CAP collapse is the consequence and dropped items are recoverable from `dropped`.

**5. [LOW] UNDER-group: distinctive bigrams require *adjacency* and *identical surface tokens*.** Today's Fable-5 collapse works only because the 5 tweets share an adjacent `("claude","fable")` (or similar) surface bigram. A paraphrase that says "Fable, Anthropic's new model" vs "Anthropic ships Claude Fable" — the first has `("fable","anthropic")`? No: `anthropic` generic, `fable` distinctive, kept as `("fable","new")`? `new` is generic, kept (`len fable>=3`) → `("fable","new")`. Second has `("claude","fable")`. **No shared bigram → today's 5-cluster would NOT collapse if surface phrasing diverges.** The test asserts it does, so the real 5 happen to share a token-adjacent phrase — but this is brittle against next week's rephrase. Acceptable as the conservative-by-design tradeoff (RC3: when in doubt don't merge), just flag that the engine is one rephrase away from the original bug resurfacing. No code change required; note it in the runbook.

**6. [LOW] Truncated `esc()` is a syntax error as shown.** The shipped snippet ends mid-function (`_esc_line` defined, never returned, `esc` never returns). Assuming the file continues past the paste, ignore — but if this is the literal file, it won't import. Confirm the tail exists.

**7. [LOW] `_GENERIC_TOKENS` has `"google"` but text yields `"googledeepmind"` only if the handle/text is literally concatenated; `@GoogleDeepMind` is stripped by `@\w+` removal in `_sig_seq`, so org tokens mostly come from body text. Minor: `"gemini"`, `"claude"`, `"gpt"`, `"grok"` are NOT generic — correct, those are the distinctive entities you want to key on. No change, just confirming the guard's intent holds.**

**8. [LOW] `groups.items()` iteration order.** Dict preserves insertion order (group-id first-seen = input order), and each group's winner is independently sorted, so the *final* `top`/`also_out` are re-sorted globally — output order is permutation-stable **for the winner set**. But `kept.extend(winners)` order feeds the final sort, which is total given Findings 1–2 are fixed. With the current inverted/ASCII-fragile tiebreak, two inputs that differ only in dup ordering *can* surface different winners only if `_winner_sort_key` ties AND ids tie — ids are unique, so winner selection is deterministic. **Winner choice is stable; final placement order is stable. The instability is confined to the Finding-1 prefix case.**

## Determinism Check
- **Union-find:** `parent[max]=min` root + `find` path-halving → root is always the lowest input index of the component, independent of union order. ✅ Permutation-stable group identity.
- **event_key first-seen (`ek_first`):** keyed by lowercased-stripped string, unions to first index → stable. ✅
- **Bigram pass:** nested `i<j` over input order, `union(i,j)` → component roots are min-index regardless of which pair fires first (union is idempotent/commutative under min-root). ✅
- **Winner sort:** deterministic given unique ids, EXCEPT the Finding-1 unequal-length-id inversion (wrong but still *deterministic* — same input always yields same wrong order). So: **deterministic yes, correct-per-spec no.**
- **`groups.items()`:** insertion-ordered, but output is globally re-sorted → iteration order doesn't leak. ✅
- **Verdict:** output is **deterministic across input permutations**; the only stability/correctness defect is the `_neg_stable` tiebreak semantics (Finding 1), which is consistent but inverted for variable-length ids.

## Verdict rationale
Core engine is sound: union-find is genuinely permutation-stable, the bigram deviation is defensibly conservative (UNDER-groups rather than OVER-groups when in doubt — the right bias, since OVER-grouping deletes real news). No crash/empty/missing-field issues (`_score_val`/`_engagement`/`_item_text`/`_stable_key` all coerce safely; empty pool short-circuits; `per_event_cap>1` slices cleanly). **Not a BLOCK** because every defect is either latent (Finding 1 needs variable-length ids) or spec-conformant-but-undocumented (Finding 3). **Not a clean APPROVE** because Finding 1 is a real tiebreak inversion masked by uniform snowflake widths — it *will* bite the moment a `url` fallback id is the stable key, and the two-pass sort fix is strictly better (simpler, total-ordered, removes Findings 1+2 together). Land the two-pass sort, add a variable-length-id tiebreak test (e.g. ids `"a"` vs `"ab"` at equal rank), and explicitly decide Finding 3's Top-demote behavior. Then APPROVE.
