## New Issues

1. **`timedOut` is referenced in the B1 catch but never defined — and the abort-recheck has a TOCTOU hole.** The catch reads `if (timedOut || abortController.signal.aborted) throw err`. `abortController.signal.aborted` exists; **`timedOut` does not appear anywhere in the evidence pack** and is introduced here with no definition. Either it's a stray symbol (build error) or it's an assumed local the PRD never specs. More substantively: a stage can throw a *non-timeout* error and then the abort fires between the throw and the catch evaluation (the wall-budget timer is async). On a soft stage that races the deadline, `signal.aborted` could be true at catch-time for an error that was *not* the timeout, causing a genuine soft failure to be re-thrown as fatal — the inverse misclassification of the one B1 set out to prevent. **Required:** define `timedOut` (or drop it and rely solely on the signal), and specify that the catch distinguishes "this error IS the timeoutFailure" (e.g. `err instanceof TimeoutFailure` / `err.kind==='timeout'`) rather than "the signal happens to be aborted now." The B1 test only covers timeout-*causes*-throw, not throw-then-abort-races; add that case.

2. **§2.2.1 still says "in addition to" parenthetically but §B3 commits to additive — and §2.5-P2.4 says "remove the legacy ratings" while Acceptance/§2.6 never restate it.** §2.2.1: *"emit the 4 enum labels per tweet instead of (or in addition to) the per-metric ratings"* leaves the in/out decision open in the body, even though B3 resolved it to **additive (both)**. Leftover "instead of" optionality in the normative section contradicts the resolved blocker. **Required:** edit §2.2.1 to drop "instead of (or in addition to)" → "in addition to (additive; legacy ratings retained until P2.4)" so the body matches §B3.

3. **The B5 freshness window is underspecified and can false-positive OR false-negative.** "`updated_at` within this run's wall-clock window" needs a concrete window. profile.ts writes `updated_at` once, early-ish, from `isoNow()`; the assert reads its *own* `Date.now()` after the rename. The gap is "stage start → write → rename → assert," seconds normally — but if the assert's window is too tight (e.g. <2s) a slow rebuild self-fails (`profile-stale` false positive); too loose (e.g. "today") and yesterday's 23:59 run passes a no-op today. **Required:** specify the window as "≥ this stage's start timestamp captured in TS before spawning the stage" (monotonic-ish lower bound), not a fixed duration. That makes "the file was written *during this stage*" provable without a brittle magic number.

4. **`low_reach_cap()` signature change is named but the call sites aren't enumerated — partial spec.** §B2 says *"`low_reach_cap()` gains a `cap_val` param (default `LOW_REACH_SCORE_CAP`)"* and evidence shows it referenced at line 304 ("X item → cap at LOW_REACH_SCORE_CAP") and line 311. If `low_reach_cap()` is called from multiple sites inside `select_shadow`/scoring, each must pass the in-function `low_reach_cap_val` or they'll silently use the module default and the override won't actually bind. **Required (small):** the diff must thread `low_reach_cap_val` into every `low_reach_cap(...)` call within the override scope, and a test must assert the LOW_REACH cap actually moves end-to-end (not just that the local var changed) — i.e. an item that would clear the default cap but not the overridden cap gets dropped.

5. **OQ4 is "must be answered before P2.1" but the answer is given in the same doc — reconcile.** §2.2 Open Q / §Remaining-OQ4 both state Quick Hits flow through the same event-collapse/forced-distribution and that `MAX_ALSO` is only a slot cap, with a test. That's effectively answered. But §2.5-P2.1 (parameterize caps/gates) is where `MAX_ALSO=5` first lands, and the routing decision changes whether `select_shadow`'s distribution logic keys off `MAX_TOP` only or both. **Required (clarity):** move the OQ4 answer into §2.2.4 normative text and confirm the existing forced-distribution/event-collapse code path is driven by the *selected* set construction, not a literal `MAX_TOP==5` assumption (Pass-1 Open Q4 flagged this; the v2 asserts a test exists but doesn't show the code reads caps generically).
