## Per-blocker verification

**B1.1 (incremental window shrink) — FIXED.** This was the real, severe blocker (silent data loss), and the fix is correct. Old code re-trimmed the merged set against a per-run `since = now-24h`, so a tweet 23h old at seed time was dropped once a rerun pushed it past 24h. New code: (a) keeps ALL existing cached tweets — the `.filter(... >= since)` is gone; (b) anchors the new-page sweep to `windowSince = existing.meta.since || since`; (c) persists the original `since` via `{ ...buildMeta(...), since: windowSince }` with correct override order (explicit key after the spread wins). The 23h→25h survival case is genuinely fixed.
- **New residual (acceptable, must acknowledge):** anchoring to the *frozen* original `since` for the whole PT day means a late-day incremental run retains a window up to ~34h wide vs a fresh sweep's 24h. This is bounded **over-inclusion**, not loss, and it self-resets every morning via the PT-day MISS. Since the canonical 7:30am deliverable is always a fresh MISS (B2/B3), Ace never sees the drift — it only affects same-day manual reruns, where keeping a few extra stale tweets is strictly safer than dropping valid ones. Correct tradeoff; just name it in the spec so it isn't "discovered" later.
- **Backfill edge (acceptable):** pre-fix cache files have no `meta.since`, so the first post-deploy incremental run on such a file falls back to the legacy shrinking behavior for that single run, then self-heals at the next PT-day MISS. <24h transient, not a blocker.

**B1.2 (idIsNewer length-then-lex → BigInt) — FIXED (code), but the regression test is NOT discriminating.** The BigInt compare is correct and strictly more robust, and the `catch` fallback to length-then-lex for non-numeric ids is sound. **However**, for decimal ids with no leading zeros, length-then-lex is mathematically identical to numeric compare — so the added regression test (`'1000…'` vs `'999…'`) **passes under the OLD code too** (verified: old returns True/False exactly as expected). The test does not pin the bug it claims to fix. The genuinely-broken inputs would be leading-zero or non-numeric ids — which real X snowflakes never produce, meaning B1.2 was a latent/theoretical bug, not a live one. The fix is still correct future-proofing; just don't let the test masquerade as proof of a regression it can't catch.

**B2/B3 (UTC day-key vs PT cron) — FIXED.** `isoDay` now uses `Intl.DateTimeFormat('en-CA', { timeZone: 'America/Los_Angeles' })`, which correctly yields zero-padded `YYYY-MM-DD` in PT. Verified all three boundary claims with real `zoneinfo` (PDT/UTC-7 in June): 07:30 PT run → `2026-06-08`; evening-before rerun (05:00Z) → `2026-06-07`; seed (20:00Z) → `2026-06-08`. The daily cron is therefore always the first run of its PT day → guaranteed MISS → clean 24h sweep, so the canonical deliverable never touches the incremental path. Design is now self-consistent with the cron schedule and the seen-list's PT dates.
